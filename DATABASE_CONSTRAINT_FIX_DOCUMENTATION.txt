1. ISSUE DESCRIPTION
================================================================================

SYMPTOM:
--------
When a CertificateIssued Kafka event was received, the CitizenKafkaConsumer
attempted to save a Document record with document_type = 'CERTIFICATE', but
PostgreSQL rejected the INSERT operation with the following error:

    ERROR: new row for relation "documents" violates check constraint
           "documents_document_type_check"

    Detail: Failing row contains (ac637a78-39e3-4d05-93c3-d38d7ac6a4d5,
            1867cb99-9903-40e7-aee1-c7a36b793cff, 2026-06-25 23:13:28.097293,
            CERTIFICATE, /api/certificates/download/CERT-3BB9221D2F0A.pdf,
            2026-06-25 23:13:27.706857).

APPLICATION IMPACT:
-------------------
- Certificate documents could not be downloaded by citizens
- Kafka consumer error was logged but the event was lost (not retried by default)
- UI would not show certificate download link since no Document record was created
- User flow broken: KYC verified → Certificate issued → BUT citizen gets nothing

ERROR LOG REFERENCE:
--------------------
    2026-06-25T23:13:28.096+05:30  INFO  CitizenKafkaConsumer :
        Received Certificate Issued event for citizen: 1867cb99-9903-40e7-aee1-c7a36b793cff,
        certNumber: CERT-3BB9221D2F0A, status: GENERATED

    2026-06-25T23:13:28.155+05:30 ERROR SqlExceptionHelper :
        ERROR: new row for relation "documents" violates check constraint
        "documents_document_type_check"

    2026-06-25T23:13:28.165+05:30 ERROR CitizenKafkaConsumer :

        could not execute statement [ERROR: new row for relation "documents" violates
        check constraint "documents_document_type_check"...]


================================================================================
2. ROOT CAUSE ANALYSIS
================================================================================

TECHNICAL ROOT CAUSE:
---------------------
The application code and the database schema were out of sync:

CODE SIDE:
  - DocumentType.java enum includes: AADHAAR, PAN, PASSPORT, CERTIFICATE
  - CitizenKafkaConsumer.handleCertificateIssued() creates Document with
    document_type = DocumentType.CERTIFICATE
  - Document entity uses @Enumerated(EnumType.STRING) → stores enum name as string

DATABASE SIDE:
  - Postgres table 'documents' had a CHECK constraint:

    ALTER TABLE documents ADD CONSTRAINT documents_document_type_check
    CHECK (document_type IN ('AADHAAR', 'PAN', 'PASSPORT'));

  - This constraint only allowed 3 types; 'CERTIFICATE' was missing

SCHEMA MISMATCH:
  - Code supports CERTIFICATE type, but DB constraint rejects it
  - When Hibernate tried to INSERT with document_type='CERTIFICATE',
    PostgreSQL's constraint validation caught it and rejected the row
  - This is a DB-level integrity check, which is correct behavior, but
    the schema was incomplete

WHY THIS HAPPENED:
  - The constraint was created initially for AADHAAR, PAN, PASSPORT documents
  - When CERTIFICATE type was added to the enum later, the DB constraint
    was not updated
  - No mechanism (like Flyway migrations) was in place to keep schema and
    code in sync
  - Hibernate's ddl-auto was likely set to 'update', which may not catch
    CHECK constraint changes


================================================================================
3. SOLUTION IMPLEMENTED
================================================================================

OVERALL STRATEGY:
-----------------
1. Update the database CHECK constraint to include 'CERTIFICATE'
2. Introduce Flyway for database schema version control
3. Create a migration file to document and manage the constraint change
4. Configure Flyway to handle the existing schema safely via baseline

FILES ADDED/MODIFIED:
---------------------

A) src/main/resources/db/migration/V1__Fix_documents_constraint.sql (NEW)
   -----------------------------------------------------------------------
   Content:

   -- Fix check constraint on documents table to include CERTIFICATE type
   ALTER TABLE documents DROP CONSTRAINT IF EXISTS documents_document_type_check;

   ALTER TABLE documents
   ADD CONSTRAINT documents_document_type_check
   CHECK (document_type IN ('AADHAAR', 'PAN', 'PASSPORT', 'CERTIFICATE'));

   Why:
   - Drops the old constraint that excluded CERTIFICATE
   - Creates new constraint that includes all 4 allowed document types
   - Use of IF EXISTS prevents errors if constraint doesn't exist
   - Versioned as V1 (Flyway naming: V[version]__[description].sql)

B) pom.xml (MODIFIED)
   -------------------
   Added dependency:

   <dependency>
       <groupId>org.flywaydb</groupId>
       <artifactId>flyway-core</artifactId>
       <version>9.22.3</version>
   </dependency>

   Why:
   - Flyway 9.22.3 is LTS and compatible with PostgreSQL 15.x
   - Version 9.22.3 chosen after testing versions 10.12.0 and 11.0.0
     (which had compatibility issues in this environment)
   - Enables automated schema version control and migration tracking

C) src/main/resources/application.yml (MODIFIED)
   -----------------------------------------------
   Changes:

   # Flyway Configuration
   spring:
     flyway:
       enabled: true
       baseline-on-migrate: true
       baseline-version: 1

   # Hibernate Configuration
   jpa:
     hibernate:
       ddl-auto: validate

   Why:
   - spring.flyway.enabled: true → Activates Flyway migration system
   - spring.flyway.baseline-on-migrate: true → Creates baseline entry for
     existing schema (solves "non-empty schema but no history" error)
   - spring.flyway.baseline-version: 1 → Marks current state as version 1
   - spring.jpa.hibernate.ddl-auto: validate → Stops Hibernate from
     modifying schema; Flyway takes responsibility

ISSUE #2: Flyway Dependency Version Incompatibility
=====================================================
Error:
  org.springframework.beans.factory.BeanCreationException:
    Error creating bean with name 'flywayInitializer':
    Unsupported Database: PostgreSQL 15.17

When: After adding Flyway and trying to start the application

Root Cause:
  - Flyway version 10.12.0 was added first
  - Flyway has internal database version compatibility matrix
  - Version 10.12.0 did not include explicit support for PostgreSQL 15.17
  - Spring Boot tried to initialize Flyway on startup, which validated
    the database version and rejected PostgreSQL 15.17 as "unsupported"
  - (Note: PostgreSQL 15.x is actually supported, but the Flyway JAR
    version didn't have the recognition code compiled in)

Versions Tried:
  1. 10.12.0 → Unsupported Database error
  2. 11.0.0 → Unsupported Database error
  3. 9.22.3 (LTS) → SUCCESS

Impact:
  Application would not start; Flyway initialization blocked by validation

Workaround (temporary):
  - Disabled Flyway (spring.flyway.enabled: false)
  - Changed hibernate.ddl-auto to 'update'
  - Applied SQL constraint fix manually via docker exec
  - App started successfully

Permanent Resolution:
  - Tested Flyway 9.22.3 LTS version
  - 9.22.3 includes proper PostgreSQL 15.x support
  - Updated pom.xml to pin version 9.22.3
  - Rebuilt and verified startup succeeded

Learning:
  - Always pin Flyway version explicitly; don't rely on transitive versions
  - Test with LTS versions for stability
  - Flyway version compatibility with DB is strict and fails fast


ISSUE #3: Flyway Schema History Table Missing (Baseline Issue)
===============================================================
Error:
  org.springframework.beans.factory.BeanCreationException:
    Error creating bean with name 'flywayInitializer':
    Found non-empty schema(s) "public" but no schema history table.
    Use baseline() or set baselineOnMigrate to true to initialize
    the schema history table.

When: After successfully fixing version incompatibility, on next startup

Root Cause:
  - PostgreSQL database 'citizenDb' already had tables (non-empty schema)
  - But no 'flyway_schema_history' table existed
  - Flyway's safety mechanism: refuses to run migrations on existing
    schemas without explicit baseline to avoid accidental migrations
    on production databases
  - Flyway wants confirmation that you understand the DB is already
    populated and migrations should start from current state

Impact:
  Spring Boot would not start; Flyway blocked initialization

Root Analysis:
  - This is EXPECTED when you adopt Flyway on an existing database
  - Flyway is correctly refusing to silently apply migrations
  - You must either:
    a) Run Flyway.baseline() manually, or
    b) Set spring.flyway.baseline-on-migrate: true in config

Resolution Applied:
  1. Added configuration in application.yml:
     spring.flyway.baseline-on-migrate: true
     spring.flyway.baseline-version: 1

  2. Rebuilt application

  3. On startup, Flyway:
     - Detected non-empty schema
     - Created 'flyway_schema_history' table
     - Inserted baseline entry (version 1, description "<< Flyway Baseline >>")
     - Applied migrations with version > 1 (none yet, so V1 not reapplied)
     - Application started successfully

Learning:
  - Baseline is required when adopting Flyway on existing databases
  - baseline-version: 1 means "current DB state = version 1 applied"
  - Future migrations start from V2, V3, etc.
  - This is correct and safe behavior


ISSUE #4: Manual SQL Applied Before Flyway Enabled
===================================================
Scenario:
  While debugging Flyway issues, we temporarily:
  1. Disabled Flyway
  2. Set hibernate.ddl-auto: update
  3. Manually ran ALTER TABLE using docker exec psql

Problem:
  - SQL was applied directly to database
  - But migration file (V1__Fix_documents_constraint.sql) existed
  - When Flyway was re-enabled, it tried to reconcile:
    "Is V1 migration already applied? Or should I run it?"

Resolution:
  - Used baseline-on-migrate: true to handle this
  - Since constraint was already manually applied, baseline
    marked the DB as "version 1 complete"
  - V1 migration was not re-run (correct behavior)
  - No data loss or duplication

Learning:
  - When manually applying SQL, ensure Flyway knows the state
  - baseline-on-migrate handles this gracefully
  - Future: avoid manual SQL if possible; use migrations from start


ISSUE #5: Command Line Tool (psql) Not Available on Host
=========================================================
Situation:
  First approach was to run SQL using 'psql' command directly in
  PowerShell

Error:
  psql : The term 'psql' is not recognized as the name of a cmdlet,
        function, script file, or operable program.

Root Cause:
  PostgreSQL client tools (psql) were not installed on Windows machine

Impact:
  Could not run SQL directly from PowerShell

Workaround Applied:
  Used Docker to run psql inside the PostgreSQL container:

  docker exec -it citizen-postgres psql -U postgres1 -d citizenDb \
    -c "ALTER TABLE documents DROP CONSTRAINT IF EXISTS documents_document_type_check;"

Learning:
  - Container provides isolation; tools don't need to be on host
  - Docker exec can run any command inside running container
  - Useful for debugging production containers (can't install tools there)

SCENARIO 3: Rollback to Previous Migration Version
===================================================

If V2 migration causes issues:

1. Remove V2__...sql file from src/main/resources/db/migration/

2. Run Flyway repair (marks failed migrations):
   docker exec -it citizen-postgres psql -U postgres1 -d citizenDb \
     -c "SELECT * FROM flyway_schema_history;"

   Look for migration with success=false

3. Delete the failed migration history:
   docker exec -it citizen-postgres psql -U postgres1 -d citizenDb \
     -c "DELETE FROM flyway_schema_history WHERE version = 2;"

4. Rebuild and restart application:
   .\mvnw.cmd clean package -DskipTests
   java -jar target/citizen-service-0.0.1-SNAPSHOT.jar

NOTE: Best practice is to always move forward with new migrations,
not rollback. Create V3 to fix V2 instead.


SCENARIO 4: Emergency - Manually Fix Database
==============================================

If migration fails critically:

1. Connect to database directly:
   docker exec -it citizen-postgres psql -U postgres1 -d citizenDb

2. Check constraint status:
   \d documents

3. Manually drop and recreate constraint:
   ALTER TABLE documents DROP CONSTRAINT documents_document_type_check;

5. Test and restart application

9. PRODUCTION RECOMMENDATIONS
================================================================================

DATABASE MIGRATION BEST PRACTICES:
==================================

1. Always Use Flyway (or Liquibase) in Production
   ✓ Version control for schema changes
   ✓ Audit trail of all modifications
   ✓ Repeatable and testable
   ✗ Never use Hibernate's ddl-auto: update in production

2. Set Proper Hibernate Configuration
   Production: spring.jpa.hibernate.ddl-auto: validate
   Staging:   spring.jpa.hibernate.ddl-auto: validate
   Dev:       spring.jpa.hibernate.ddl-auto: update (optional)

3. Naming Convention for Migrations
   Use: V[number]__[description_in_snake_case].sql
   Example:
     V1__Fix_documents_constraint.sql
     V2__Add_certificate_expiry_column.sql
     V3__Create_audit_table.sql

   Benefits:
     - Flyway automatically discovers and orders migrations
     - Versions must be sequential; gaps cause errors
     - Description helps with audit and understanding

4. Migration File Content Guidelines
   ✓ Make each migration idempotent (safe to run multiple times)
   ✓ Use "IF EXISTS" / "IF NOT EXISTS" clauses
   ✓ Add comments explaining business reason
   ✓ Keep migrations small and focused on one change
   ✗ Don't mix DDL (schema) and DML (data) unless necessary
   ✗ Don't include comments with semicolons (breaks batch execution)

5. Testing Migrations Before Production
   - Apply migration to DEV environment first
   - Verify application starts successfully
   - Test relevant features end-to-end
   - Run database backups before production
   - Have rollback plan ready

6. Monitoring and Logging
   - Enable Flyway debug logging:
     logging.level.org.flywaydb: DEBUG
   - Monitor Kafka consumer error logs
   - Set up alerts for constraint violation errors
   - Periodically review flyway_schema_history table

7. Database Backup Strategy
   Production: Daily full backups
   Before migrations: Point-in-time backup
   Retention: 30 days minimum
   Test restore procedure quarterly

8. Version Control
   - Commit migration files to git
   - Tag releases with migration version
   - Document breaking changes in release notes
   - Never edit already-applied migrations

9. Baseline vs Clean Migration
   Baseline: Use when adopting Flyway on existing database
   Clean:    Only use in dev; drops and recreates schema
   Never:    Use baseline-on-migrate in production without review

HANDLING MIGRATION CONFLICTS:
=============================

Situation: Two branches add migrations at same time (V2 in both)

Resolution:
1. First branch merges: Migration is V2__feature_a.sql (applied)
2. Second branch needs rebase:
   - Rename V2__feature_b.sql → V3__feature_b.sql
   - Update any version references in tests
   - Commit: git rebase main
   - Now applies in order: V2 (feature_a), then V3 (feature_b)

This is why sequential versioning matters!


EMERGENCY: Delete All Data and Restart Fresh
============================================

If you need to completely reset for testing:

1. Disable Flyway:
   spring.flyway.enabled: false

2. Clear tables (careful!):
   docker exec -it citizen-postgres psql -U postgres1 -d citizenDb \
     -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"

3. Re-enable Flyway:
   spring.flyway.enabled: true
   spring.flyway.baseline-on-migrate: false

4. Restart application:
   Flyway will recreate all tables from migrations (V1, V2, V3, ...)
   flyway_schema_history will be empty initially, then populated


VIEWING MIGRATION HISTORY:
==========================

Command:
  docker exec -it citizen-postgres psql -U postgres1 -d citizenDb \
    -c "SELECT version, description, type, script, success, installed_on
        FROM flyway_schema_history ORDER BY installed_rank;"

Output shows:
- version: Migration version (1, 2, 3, ...)
- description: File name / purpose
- type: SQL or JDBC
- script: File name
- success: true/false (did it apply without error?)
- installed_on: Timestamp when applied

Use this to debug, audit, and track all schema changes.


COMMON ISSUES AND TROUBLESHOOTING:
==================================

Issue: "Validate failed: Migration checksum changed"
Reason: Migration file was edited after being applied
Fix:
  1. Never edit migration files after applied
  2. Create new migration (V+1) to fix the issue
  3. If accidental, revert file to original state
  4. Run: flyway repair (updates checksum in history)

Issue: "Flyway refuses to run on non-empty schema"
Reason: DB has tables but no flyway_schema_history
Fix:
  1. Set baseline-on-migrate: true (one-time)
  2. Or manually: flyway baseline command
  3. Flyway will create history table and baseline entry

Issue: Migration takes too long / locks tables
Reason: Large data migration on big table
Fix:
  1. Use CONCURRENTLY for indexes: CREATE INDEX CONCURRENTLY ...
  2. Use batch operations for data migrations
  3. Test on staging first with production-like data
  4. Schedule for maintenance window if needed

Issue: "Schema version is not 1" or migration order wrong
Reason: Non-sequential version numbers
Fix:
  1. Check file names: V1, V2, V3 (no gaps!)
  2. Rename files to sequential order
  3. Check git history for orphaned migrations
  4. flyway repair / reset if needed
